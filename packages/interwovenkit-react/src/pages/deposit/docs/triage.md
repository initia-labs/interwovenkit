Linear 이슈 $ARGUMENTS를 아래 워크플로로 처리하라. **인자가 없으면 [Deposit 프로젝트](https://linear.app/initia-labs/project/deposit-58d86a8edeec/issues) 전체가 대상이다** (`list_issues`의 `project: "deposit-58d86a8edeec"`). 부모 이슈가 주어지면 그 서브태스크 전체를, 서브태스크(또는 일반 이슈)가 직접 주어지면 해당 이슈만 대상으로 한다. 모호하거나 궁금한 것이 있으면 작업 전 혹은 도중에 질문하라.

## 승인 원칙 (모든 Linear 쓰기 작업)

- Linear 읽기(이슈·댓글 조회, `extract_images`)와 로컬 조사(코드 리딩, curl 재현, 브라우저 재현)는 자유롭게 수행한다.
- **모든 Linear 쓰기 작업은 사용자 승인 후에만 실행한다. 예외 없다.** 댓글 게시·수정만이 아니라 이슈 생성, 본문(description) 수정 — 자체 batch 이슈 본문 기록 포함 —, 상태 변경, assignee 변경, 관계(`blocked by` 등) 변경, 라벨·우선순위 변경 전부가 대상이다.
- 진행 방식: 조사·검증을 마친 뒤 수행하려는 쓰기 작업 전체를 하나의 변경 계획으로 묶어 보고한다 — 항목마다 무엇을(대상 이슈·필드·내용) 왜(근거) 바꾸는지 명시한다. 승인받은 항목만 실행하고, 부분 승인이면 승인된 항목만 실행한다.
- 이 문서의 다른 서술("즉시 반영한다", "변경한다", "기록한다" 등 실행형 문장)은 모두 **승인 후 실행**으로 읽는다. 이 원칙이 다른 모든 서술보다 우선한다.

## 공통 원칙

- 메시지는 핵심만 간결하게 작성한다.
- 사용자가 직접 외부 채널(텔레그램 등)에 공유해야 하는 메시지는 코드블록으로 감싼 복붙 원문으로 제공한다. 본문에 헤딩·볼드 등 구조 마크업은 쓰지 않되, API 경로·파라미터·에러 코드 등은 인라인 코드 백틱으로 감싼다 (텔레그램이 백틱을 모노스페이스로 렌더링한다). 텔레그램은 백틱 바로 앞뒤에 괄호 같은 문자가 붙으면 포맷팅이 깨지므로, 인라인 코드를 괄호로 감싸지 말고 백틱 경계에 공백이 오도록 문장을 재배열한다.
  - **백틱 누락 최종 점검 (필수)**: 초안을 사용자에게 제시하기 직전, 코드성 토큰 전부에 백틱이 감겨 있는지 하나씩 확인한다 — transaction id, intent id, 엔드포인트·URL 경로, HTTP 상태 코드, 헤더 이름(`Referer` 등), 필드 이름·값(`waiting_for_deposit` 등), 파라미터가 대상이다. 점검 없이 초안을 출력하지 않는다.
- 외부 메시지에 "next batch" 같은 내부 운영 용어를 쓰지 않는다.
- **코멘트는 해당 이슈 안에서 자기완결적으로 작성한다**: repo 내부 문서, 세션 대화 맥락, 독자가 접근할 수 없는 커밋(drop됐거나 rebase 전 sha) 등 이슈 밖 정보를 전제하는 서술("첫 수정", "내부 플랜 문서" 등)을 넣지 않는다. 그런 맥락이 필요하면 코멘트 안에서 풀어서 서술한다.
- **조사·플랜 산출물은 repo 임시 문서가 아니라 이슈 코멘트로 남긴다**: 담당자·상태·분류·판정 근거처럼 Linear가 원본인 정보를 repo 문서로 집계·스냅샷하지 않는다 (이슈가 움직일 때마다 부패한다). 구현 지식(기각된 대안과 이유, 제약, 검증 계획)도 자기완결 코멘트로 압축해 남기는 것을 우선하고, 코멘트 매체에 담기 어려운 분량만 예외적으로 문서화한다.
- **외부 게시물에 커밋 해시를 언급하지 않는다**: Linear에는 사용자가 검증할 동작과 배포 상태를 기록한다. 커밋 해시는 사용자 보고에만 포함한다.

- 제외: 이미 완료(Done/Canceled)된 이슈, 이전 사이클에서 처리해 In Review 상태인 이슈, 백엔드 담당자에게 이미 할당된 이슈. 단, 사용자가 이슈를 직접 지정한 경우는 제외 조건에 해당해도 처리 대상이다 — 제외 사유를 알리고 진행 여부를 확인하라.

### Onramper 팀 문의

서드파티로 분류되어 Onramper 측 확인·수정 요청이 필요한 경우:

문의·제보는 예외 없이 배치로 발송한다. 이전 배치의 응답을 기다리지 말고 항목별 응답을 독립적으로 추적한다.

**수집 기준** (배치 포함 여부):

1. **해결 주체가 Onramper로 한정되는가**: 프론트엔드 완화(폴백, 라벨링, 필터링)로 사용자 영향이 실질적으로 해소되면 완화를 우선 적용하고 수집하지 않는다. 완화 후에도 Onramper 측 인지가 필요한 근본 원인이 남으면 제보 항목으로 수집한다.
2. **추적 가능한 증거**: 항목마다 curl 재현, transaction id, 스크린샷 등 Onramper가 자체 로그에서 추적할 수 있는 증거를 첨부한다. 일시적 관찰(리스팅 변동, 단발 실패)은 리포터에게 재발 시 증거 확보를 요청하고, 증거가 확보된 시점에 수집한다. 증거 미비로 보류한 항목은 판단 근거를 Linear 코멘트로 기록한다.

**추적**: 모든 문의는 [EXP-876](https://linear.app/initia-labs/issue/EXP-876/onramper-inquiries-sent-awaiting-response) 하나에서 관리하고 배치별 이슈를 만들지 않는다. 각 항목에 발송 원문, 텔레그램 날짜·순번·item 번호를 `Sent as`로 기록하고 대상 이슈를 EXP-876에 `blocked by`로 연결한다. 회신 원문과 검증 결과를 기록한 뒤 대상 이슈를 갱신하고 unblock한다. 모두 Linear 승인 대상이다. 후속 확인까지 끝난 항목은 헤딩에 `~~`를 적용해 뒤로 옮긴다. 제보자가 대상 이슈를 Done으로 완료하면 outbound를 중단하고 날짜·종결 사유·`resolved` 또는 `moot`를 기록한 뒤 관계를 제거한다. EXP-876은 닫지 않는다.

**할당**: EXP-876은 발송 담당 Sim에게, 우리 수정 없이 회신 추적만 남은 대상 이슈는 파트너 채널을 확인할 수 있는 Jack에게 할당한다. 자체 수정이 남으면 2단계 담당자를 따른다.

**초안 관리**: 발송 원문은 EXP-876에만 기록한다. 대상 이슈에는 조사 결론과 발송 사실만 남긴다.

**초안 형식**: 항목마다 `Symptom` 1~2문장, `Evidence` 최대 3개, `Question` 1~2개 순서로 쓴다.

**API 키·재현 일자를 문의 메시지에 넣지 않는다**: 상대는 우리 계정을 이미 알고 있고, 매번 반복하면 본문만 길어진다. 요청받으면 그때 제공한다. 대신 상대가 그대로 실행해 같은 응답을 얻을 수 있는 형태로 재현 경로를 적는다 — 지역·계정에 의존하는 파라미터(`country` 등)를 명시해 실행 위치와 무관하게 동일한 결과가 나오게 하고, 값이 시세로 흔들리는 필드는 특정 호출의 예시임을 밝힌다.

**QA 리포터 협업**: 배치 운영 방침, 레이블 관리, 리포트 시점 1차 판별 요청은 [EXP-872 코멘트](https://linear.app/initia-labs/issue/EXP-872/sardine-registration-only-allows-us-addresses#comment-b262777c)로 최초 안내를 완료했다. 이슈마다 반복하지 않는다. 새 Onramper 대상 이슈에는 배치에 수집됐다는 사실만 간단히 코멘트로 남긴다 (게시는 6단계의 승인·reply 규칙을 따른다).

**발송 절차** (배치가 준비되면):

1. **발송 전 재검증**: 배치의 전 항목이 오늘 기준으로도 재현되는지 curl로 확인한다. 라이브 재현이 안 되는 항목(간헐 증상, 과거 주문·스크린샷 기반 증거)은 그 사실을 구분해 사용자에게 보고한다.
2. **문의 초안 공유**: 배치에 포함된 항목을 하나의 메시지로 통합해 사용자에게 공유한다. 근본 원인이나 성격이 동일한 항목(예: capability 데이터 불일치)은 하나로 병합한다. 팀은 이미 Onramper 텔레그램 채널에 있고 문의를 주고받은 이력이 있으므로, 채널·연락처 안내 없이 바로 붙여넣을 수 있는 본문만 작성한다. 통합 메시지는 다음을 지킨다:
   - 항목은 심각도 순으로 배열하고, 각 항목은 초안의 Symptom → Evidence → Question 구조를 유지한다.
   - 날짜와 API 키는 넣지 않는다 (위 규칙). 라이브 API로 지금도 재현되는 증거와 과거 세션 증거(스크린샷·transaction id)는 구분해 서술한다.
   - 스크린샷·녹화·transaction id는 선제 첨부하지 않고 "available on request"로만 언급한다.
3. **문의 후 Linear 반영**: 사용자가 문의 전달을 확인하면 EXP-876에 해당 항목의 as-sent 원문과 `Sent as` 포인터를 기록하고, 각 이슈 상태를 In Progress로 변경하며, 문의 전문이 아니라 **핵심만 간단히** 요약한 코멘트를 단다 — 조사 결론(원인이 Onramper 측임) + Onramper에 문의했고 응답 대기 중이라는 사실. 게시는 6단계의 reply 규칙을 따른다.

## 3. 병렬 조사

대상 이슈가 여러 개면 이슈별 서브에이전트를 **한 메시지에서 동시에 launch**해 병렬로 처리한다. 단, 아래 두 가지를 먼저 점검한다.

### 그룹화

- 두 이슈가 유사하거나 사실상 같은 것을 바라보고 있으면 **하나의 작업 단위로 묶어 한 에이전트가 처리한다**. 판단 단서: 같은 화면·플로우·컴포넌트, 같은 에러 메시지, 증상 서술이 겹침, 중복 리포트 의심.
- 나눠서 병렬로 고치면 같은 코드를 두 곳에서 건드려 충돌하거나, 같은 원인에 서로 다른 수정이 생긴다.
- 수집 단계에서 확신이 없으면 조사·검증까지는 별도로 진행하되, 원인이 같다고 밝혀지는 즉시 작업 단위를 병합하고 Linear에는 각 이슈별로 결과를 반영한다.

### 공유 자원

병렬 서브에이전트에는 읽기 전용 작업(코드 리딩, Linear 조회, 라이브 API curl 재현)만 맡기고, 아래 공유 자원을 쓰는 작업은 직렬화한다:

| 공유 자원                 | 규칙                                                                                                      |
| ------------------------- | --------------------------------------------------------------------------------------------------------- |
| working tree · git        | 파일 수정과 커밋은 병렬 금지. 수정 대상 파일이 겹칠 수 있는 이슈는 같은 작업 단위로 묶거나 순차 처리한다. |
| 개발 서버 · mock 서버     | 세션 전체에서 한 벌만 사용한다. 에이전트마다 새로 띄우지 않는다 (포트 점유 확인 규칙 동일).               |
| 브라우저 (Playwright MCP) | 단일 브라우저 세션이므로 동시 조작 불가. 브라우저 재현·E2E 검증은 한 번에 하나씩 순차 수행한다.           |

이슈별 코드 조사와 curl 재현은 병렬로, 브라우저 재현·수정·커밋은 순차로 수행한다.

## 4. 수정 전 검증

이슈가 실제로 유효한지, 진단한 원인이 맞는지 실증한 뒤에만 고친다.

다음 관점을 함께 검토한다.

- **UI/UX**: 기능적 결함이 없어도 사용성 결함은 유효한 이슈다 — 피드백 지연, 불명확한 상태 전이, 다음 행동(next step)의 부재, 에러 복구 경로 없음 등.
- **디자인 정합성**: 구현과 디자인 스펙(Figma)·디자인 시스템(토큰, 컴포넌트 변형) 간 불일치를 검토한다. 기능 버그가 아니면 Jennie 라우팅 대상이다.
- **보안**: 재현 과정에서 관찰되는 입력 검증 누락, 민감 정보 노출, 신뢰 경계 위반은 원 이슈의 스코프와 무관하게 별도로 보고한다.
- **코드 복잡성**: 수정안이 유지보수 비용이나 회귀 위험을 키우면 그대로 진행하지 말고 대안(설계 변경, 스코프 조정, 의도적 미수정)을 트레이드오프와 함께 제시한다.

검증 수단:

- **라이브 API 재현**: 이슈에 포함된 curl을 그대로 실행해 현재도 재현되는지, 백엔드에서 이미 수정됐는지 확인한다.
- **geo 의존 동작은 단일 IP로 판정하지 않는다**: Onramper의 provider 리스팅·결제수단·한도는 요청 IP의 국가로 필터링된다. 로컬 IP(한국) 한 곳에서 관찰한 결과를 "모든 비-US 국가에서 그렇다"처럼 일반화하면 안 된다 — 국가별 allowlist라서 다른 나라에서는 정반대 결과가 나온다. `country` 파라미터를 명시하면 IP와 무관하게 특정 국가를 재현할 수 있으므로(`/quotes/{fiat}/{crypto}?…&country=th`, `/supported/payment-types/{fiat}?…&country=th`), 리포터의 국가와 대조군 국가를 함께 넣어 비교한 뒤 결론을 낸다. 리포터의 실제 판정 국가는 `GET /supported/defaults/all?type=buy`의 `message.recommended.country`로 확인하며, 이는 VPN 여부를 다투는 대신 Onramper 자신의 판정을 근거로 삼는 방법이다.
- **코드 리딩으로 메커니즘 특정**: 증상이 나올 수 있는 경로를 전부 나열하고 스크린샷 증거로 소거한다.
- **브라우저 재현**: `examples/vite` + Playwright MCP + 테스트 지갑(`INITIA_TEST_MNEMONIC`, 없으면 공개 테스트 mnemonic `test test … junk`). 장애 조건은 `window.fetch` 몽키패칭으로 주입한다.
- **수정 전 코드로 원 버그 재현**: 수정을 만든 뒤 `git stash`/`checkout`으로 수정 전 상태를 임시 복원(HMR 반영)해 원 버그를 직접 재현하고, 복원 후 수정 동작과 대비한다.
- 가짜 입금, 상태 강제 전이, 지연과 오류 주입은 mock 서버의 `/__mock/*` control endpoint를 사용한다([mock 실행](../../../../../../mock/README.md#http-control)).
- 개발 서버는 포트 점유를 먼저 확인하고, 다른 체크아웃의 서버를 건드리지 않는다.

검증 결과에 따라 Linear 변경 계획을 세운다. 실행은 승인 후에만 한다.

- **유효 (수정 착수)**: 이슈 상태를 In Progress로 변경하고 5단계로 진행한다.
- **유효하지 않음 (재현 불가, 이미 수정됨, 의도된 동작, 서드파티 노이즈 등)**: 근거(재현 시도 내용, 코드·API 증거)를 담은 반박 댓글 초안(한국어·영어)을 작성해 사용자 승인 후 게시하고, 수정하지 않는다. 게시는 6단계의 reply 규칙을 따른다. **취소가 권장되는 경우**: 코멘트에 리포터 멘션과 함께 Canceled 처리를 권장한다고 명시하고, 이슈 상태를 In Review로 전환한다 — 최종 취소 판단은 리포터가 한다. 직접 Canceled로 바꾸지 않는다.

## 5. 수정, 검증, 커밋

- 프로젝트 컨벤션(AGENTS.md)을 따르고, 판단 로직은 순수 함수로 분리해 co-located 테스트를 추가한다. 관련 문서(`pages/deposit/README.md` 등)를 현재 동작에 맞게 갱신한다.
- **코드 코멘트에 이슈 ID(EXP-XXX)를 쓰지 않는다**: 이슈 참조는 커밋 메시지 트레일러(`Closes`/`Refs`)에만 둔다. 코드 코멘트는 이슈 번호 없이도 맥락이 서도록 쓴다.
- `pnpm test` / `pnpm typecheck` / `pnpm lint` 통과 + 브라우저 E2E로 수정 후 동작, 자동 회복 경로, happy path 무손상을 확인한다.
- 이슈당 1커밋. conventional commit + 본문에 원인·수정 요약 + `Closes EXP-XXX`. push는 차단되어 있으므로 사용자에게 요청한다.
- 모든 이슈의 커밋이 끝나면 현재 branch 상태와 검증 결과를 보고한다. Branch 이동과 history 변경은 자동으로 수행하지 않는다.

## 6. 보고와 Linear 마무리

- 사용자에게 보고: 이슈별 분류 결과, 원인, 검증 증거(재현 → 수정 후 대비), 커밋 해시, 댓글 초안(한국어·영어).
- **모든 Linear 쓰기는 승인 후에만** ([승인 원칙](#승인-원칙-모든-linear-쓰기-작업)): 댓글은 사용자 승인을 받고 영어본을 게시하며, 이슈 생성·본문 수정·상태·assignee·관계 변경도 변경 계획으로 보고해 승인받은 뒤 실행한다.
- **댓글은 항상 기존 쓰레드의 답글(reply)로 단다**: 이슈에 기존 코멘트가 있으면 새 최상위 코멘트를 만들지 말고, `save_comment`의 `parentId`에 해당 쓰레드 최상위 코멘트 id를 지정해 reply로 게시한다. 기존 코멘트가 하나도 없을 때만 최상위 코멘트를 만든다.
- **게시된 코멘트의 정정·후속은 그 코멘트를 직접 수정한다 — 단, 아직 아무도 읽지 않았을 때만**: 같은 조사의 후속 분석, 결론 변경, 작업 결과 반영은 정정 코멘트나 reply를 새로 달지 말고 `save_comment`의 `id`로 기존 자기 코멘트를 수정해 하나의 최신 상태로 유지한다. 이후 코드 변경으로 코멘트의 사실 서술이 구식이 된 경우도 같다 — 코드가 게시된 코멘트의 서술을 바꾸는 변경일 때는 해당 이슈의 기존 코멘트를 점검해 함께 정정한다. **그러나 누군가 그 코멘트를 읽었다는 신호(반응 이모지, 답글, 인용, 후속 조치)가 확인되면 직접 수정하지 않는다** — 읽은 사람은 수정 사실을 통지받지 못해 구버전 정보로 행동하게 된다. 이때는 새 정정 코멘트(reply)를 달아 무엇이 어떻게 바뀌었는지 명시하고, 필요하면 읽은 당사자를 멘션한다. 판단이 애매하면(오래 전 게시, 다수 참여 쓰레드) 새 코멘트 쪽을 택한다.
- 사용자가 push를 확인해 주면: 이슈 상태를 In Review로 변경하고, 리포터를 `@displayName`으로 멘션해 재검증 포인트(무엇이 어떻게 보여야 하는지)를 명시한 댓글(위 reply 규칙 동일 적용)을 단다. 테스트 URL과 빌드 반영 시점을 함께 안내한다.
- **게시한 코멘트의 링크를 마지막 보고에 포함한다**: Linear에 코멘트를 게시했다면 해당 코멘트 링크(`<이슈 URL>#comment-<코멘트 id 첫 세그먼트>`)를, 코멘트 없이 이슈만 갱신했다면 이슈 링크를 사용자 보고에 넣는다.
