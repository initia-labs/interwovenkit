# E2E 테스트 — 사람 수동 검증

> **개발용 임시 문서.** 개발 중에만 쓰고 구현이 안정화되면 삭제하므로, 코드 주석에서 이 문서를 링크하거나 참조하지 마라.

> 사람은 이 checklist로 AI가 재현할 수 없는 실결제, 실입금, 실기기 동작을 검증한다. 반복 가능한 기능 검증은 [1_REVIEW_E2E_AI.md](./1_REVIEW_E2E_AI.md), 화면 state는 [1_REVIEW_E2E_SCREENS.md](./1_REVIEW_E2E_SCREENS.md), 디자인은 [3_REVIEW_DESIGN.md](./3_REVIEW_DESIGN.md)를 참조한다.

## 검증 순서와 원칙

사람 검증은 파일 번호 순서로 진행한다: **1 기능 사용(이 문서 + [1_REVIEW_E2E_AI.md](./1_REVIEW_E2E_AI.md)) → 2 코드 리뷰([2_REVIEW_CODE.md](./2_REVIEW_CODE.md)) → 3 디자인 비교([3_REVIEW_DESIGN.md](./3_REVIEW_DESIGN.md))**. 돈이 오가는 기능에서 가장 치명적인 것은 동작 버그이고, 디자인은 가장 되돌리기 쉬운 레이어라 마지막이다.

- **사람 작업 전에 AI 셀프 검증을 소진시킨다**: `/code-review`, `pnpm test`·`typecheck`, Playwright MCP 시나리오. 기계가 잡을 수 있는 것은 사람 시간에 올리지 않는다.
- **스펙 대조**: AI는 구현이 막히면 요구사항을 미묘하게 바꿔치기한다. [API_DEPOSIT.md](./API_DEPOSIT.md) 등 스펙 문서와 실제 동작을 대조하는 것은 사람만 할 수 있는 일이며, 사실상 가장 중요하다.
- **반복 가능하게 투자한다**: 발견한 버그마다 회귀 테스트(Vitest/Playwright)를 AI에게 작성시키면 다음부터 사람 검증 범위가 줄어든다. 사람의 역할은 라인 검사자가 아니라 **스펙 검증자 + 검증 인프라 설계자**다.

## 2. Deposit via address

실 API 자동화 경계는 **실입금 도착 전**까지다(주소 발급·폴링 시작까지는 [1_REVIEW_E2E_AI.md](./1_REVIEW_E2E_AI.md)가 다룬다). 온체인 도착 이후의 **화면 검증**은 mock으로 AI가 대체하므로([mock 환경](./1_REVIEW_E2E_AI.md#mock-api-환경-선택)), 이 섹션은 실자산·실백엔드 검증이다.

### 온체인 도착 → 추적 화면 (레이어 3)

새 지갑은 `deposits`가 빈 목록이라 QR 화면에 머무는 것이 정상이며, 추적 화면과 처리중/완료/실패 버킷은 실입금 감지 후에만 진입한다(레이어 구분은 [3번의 표](#결제kyc-단계-테스트-프로덕션-스모크) 참조). cash 스모크 전에 독립적으로 검증하려면:

**절차**

1. 크립토 경로("Deposit via address")로 입금 주소를 발급받는다. 모바일 실기기로 수행하면 QR 스캔 동선([실기기/실지갑](#실기기실지갑))도 함께 확인된다.
2. Supported network 중 하나에서 최소금액 이상의 실자산을 해당 주소로 송금한다(실자금 소모, 백엔드 파이프라인·체인 confirm 대기).

**기대 결과**

- 입금이 감지되면 QR 화면이 추적 화면("Confirming your deposit…")으로 바뀌어야 한다.
- 추적 화면이 Confirming → Transferring → "Transfer complete" 순서로 진행해야 한다("Transaction complete"는 onramp 경로 전용 문구다).
- 진행 중에 화면을 나갔다가 다시 들어오면 처리중 버킷에 같은 입금이 다시 보여야 한다.

## 3. Buy with cash/card

자동화 경계는 **결제 직전**까지다: checkout intent 생성 + provider 결제 페이지 새 탭 + Processing 화면의 감지 폴링 시작까지(`DepositTracking`은 실입금 감지 후에만 진입). 결제 페이지에서 카드를 입력하는 실제 결제/KYC는 sandbox가 없어 **프로덕션 소액 실결제 스모크가 유일한 수단**이다.

### 결제/KYC 단계 테스트 (프로덕션 스모크)

**이 스모크의 산출물은 백엔드 전달용이기도 하다.** 백엔드가 이벤트/서비스 호환성 검증용 완료된 Onramper tx 예시를 요청했는데, 현재는 결제 미진행 checkout intent(`01KWV8P3BPB8Z2NKY6ZVNPGWGC`)뿐이다. 스모크 결제를 완료하고 아래 절차 5단계의 `GET /transactions/{id}` 응답을 백엔드에 전달한다.

| 레이어 | 대상                    | 방법                                                                | 카드   |
| ------ | ----------------------- | ------------------------------------------------------------------- | ------ |
| 1      | 조회/폼/주소/추적 시작  | [1_REVIEW_E2E_AI.md](./1_REVIEW_E2E_AI.md) 자동화, throwaway 니모닉 | 불필요 |
| 2      | checkout → 결제/KYC     | 프로덕션 소액 실결제 스모크(출시 직전 1회)                          | 실카드 |
| 3      | 온체인 도착 → 완료 화면 | 레이어 2 스모크에 포함, 또는 크립토 경로 실입금                     | 불필요 |

- **레이어 1**: 과금이 없다(GET·주소 파생뿐). 코드 변경 시 회귀 검증은 이 레이어 + checkout 프록시 200 확인으로 갈음한다.
- **레이어 2**: 반복 불가능하므로 실카드 소액 결제를 출시 직전 1회만 수행한다.
- **레이어 3**: 스모크의 실결제로 소스 크립토가 입금 주소에 실제 도착하므로 cash 경로의 완료 화면("Transaction complete")까지 한 번에 검증된다. 스모크 전에 완료 화면만 확인하려면 [크립토 경로 실입금](#온체인-도착--추적-화면-레이어-3)으로 대체한다.

**sandbox 불가 경위 (재요청 방지용 기록)**

- staging(`https://api-stg.onramper.com`)은 살아 있으나 내장 prod 키로는 빈 껍데기다(`/supported`가 빈 목록, quotes는 "No providers available"). 별도 `pk_test_` 키가 필요해 sandbox 자격증명을 요청했으나 **발급 거절**: sandbox 환경이 불안정하고 ramp sandbox들이 E2E testnet 트랜잭션을 지원하지 않으며 프로덕션 테스트만 권장한다는 답변. 재요청하지 않는다.
- `GET /transactions/{id}`는 서버측 전용이다(pk만으로 401, 잘못된 secret은 403 — prod 실측). `x-onramper-secret`(webhook secret) 헤더가 필수라 프론트 폴링은 불가능하다([API_ONRAMPER.md](./API_ONRAMPER.md#fiat-단계-추적)).

### 실행 절차 (프로덕션 스모크)

출시 직전 1회 수행한다. 가능하면 모바일 실기기로 수행한다 — provider 결제 페이지 redirect 등 딥링크·앱 전환 동선([실기기/실지갑](#실기기실지갑))이 함께 검증된다. 사전 조건: 백엔드가 **prod webhook secret**(`x-onramper-secret`용)을 보유해야 5단계의 tx 캡처가 가능하다 — 미보유면 Onramper에 요청한다(sandbox와 무관한 별개 자격증명).

1. **기동** — 기본(mainnet) 환경으로 띄운다. Onramper 키와 Deposit API 프록시 모두 prod가 내장/배포돼 있어 env 오버라이드가 필요 없다.
2. **Buy 제출** — Deposit → 자산 선택 → "Buy with cash/card"를 누르고, Pay 필드 아래 표시되는 최소 구매액 근처의 소액을 입력한 뒤, 최적 quote의 provider로 Buy를 누른다.
   - 기대: 누르는 즉시 버튼이 비활성(스피너)돼야 한다. 연타/중복 제출 방지는 실제 checkout intent가 생성돼 자동 테스트에서 확인할 수 없어 이 1회가 유일한 검증 기회다.
3. **checkout 확인** — `transaction_id`를 기록한다.
   - 기대: `POST /v1/onramper/checkout`이 200 + `{transaction_id, url}`로 응답하고, provider 결제 페이지가 새 탭으로 열려야 한다.
4. **결제 완료** — 결제 페이지에서 실카드로 이메일 검증 → KYC → 결제를 완료한다.
5. **fiat 단계 상태 캡처** — 백엔드가 조회한다(webhook secret이 필요해 서버측에서만 가능):

   ```
   curl -H "Authorization: pk_prod_..." -H "x-onramper-secret: <webhook secret>" \
     https://api.onramper.com/transactions/<transaction_id>
   ```

   - 기대: `status`가 진행하다 최종 `completed`가 돼야 한다.
   - **이 응답이 백엔드 이벤트/상태 호환성 검증용 tx 예시다 — `transaction_id`와 함께 백엔드에 전달한다.**

6. **온체인 도착** — 소스 크립토가 입금 주소로 도착할 때까지 기다린다.
   - 기대: `DepositTracking`이 Confirming → Transferring → "Transaction complete" 순서로 진행해야 한다(레이어 3 동시 검증).

## 경로 공통

### failed/below_minimum 화면

상태는 백엔드가 결정하므로 프론트에서 인위적으로 재현할 수 없고, 디자인도 미확정이다. 디자인 확정 후 백엔드와 협의해 검증한다 — 후보: 최소금액 미만 실입금으로 `below_minimum` 유발(자금 처리 정책 사전 확인 필요), 또는 백엔드 dev 환경에서 상태 주입. `failed`는 인위적 유발 수단이 확인된 바 없어 백엔드 협조가 필수다.

### 실기기/실지갑

자동화는 데스크톱 Chrome + 인메모리 테스트 지갑뿐이다. 출시 전 1회 이상, testnet이 아닌 **실제 자산·실제 지갑·실기기**로 주요 플로우를 확인한다.

- **모바일 실기기**: 터치 타겟, 뷰포트. 경로별 항목은 해당 섹션에 표기했다(2번: QR 스캔 동선, 3번: 결제 redirect 딥링크).
- **브라우저 확장 지갑**: 실지갑 연결·서명 UX(테스트 커넥터는 인메모리 서명이라 확장 지갑 승인 플로우를 거치지 않는다).
